Astra単体と、AstraがGPT-5.6 Solをまとめる協調構成をISUCON11予選で比較しました。**2026年9月13日、親子制御を変えて、両方式をもう一度3時間ずつ実行した結果を追記しました。** 初回と再実行は構成が異なるため、同条件の反復試行としては扱いません。

結論は、**今回の協調構成の効率優位は確認できなかった。ただし、最高値だけでは結果を説明できず、制御器にも直すべき不具合が見つかった**、です。

このZenn記事は要点版です。初回と再実行の全表、親子の稼働タイムライン、公開用JSON・CSVは個人サイトにまとめています。

## ISUCON11はどんな問題か

ISUCONは、Webサービスの機能を保ちながら、限られたサーバーで性能を改善する競技です。利用者を模したベンチマーカーが、正しさと性能を判定します。

今回のISUCON11予選「ISUCONDITION」は、椅子から届く状態データを保存し、履歴やグラフを返すサービスです。継続的な書込みと読取り・集計を同時にさばく必要があり、SQL、キャッシュ、CPU、複数台の配置などを改善します。

## 再実行：最高値と再起動後のスコアを分ける

再実行は9月13日11:14:32〜14:14:32 JST。各方式180分・1試行で、競技3台＋ベンチ1台をそれぞれ用意し、合計8 EC2で同時に走らせました。

![再実行の時間内最高値は単体556,115、協調409,477。全台再起動後は439,762と429,895で両方合格](/images/astra-sol-isucon/sdk-rerun-20260913/outcome.png)

| 再実行の指標 | Astra単体 | Astra＋Sol |
|---|---:|---:|
| 時間内最高有効スコア | **556,115** | 409,477 |
| 最高版の全台再起動後・1回 | **439,762 / pass** | 429,895 / pass |
| 通常計測 成功 / 失敗 | 40 / 3 | 23 / 1 |
| 診断計測 完了 / 未完了 | 3 / 1 | 7 / 0 |
| 記録総トークン（親＋子） | 40,948,900 | 46,719,114 |
| 非キャッシュ入力 | 1,018,380 | 1,718,097 |
| 出力 | 177,176 | 390,713 |

時間内最高値は単体が約1.36倍でしたが、**再起動後の差は約2.3%**でした。確認も各1回なので、この差から一般的な優位性や再現性は主張しません。最高版の点数の変化も、再起動だけの影響とは分離できていません。

単体の最後の未完了1件は診断runで、通常失敗3件とは別です。未完了・診断・時間外の走行は時間内最高値に加えていません。

![再実行のスコアと記録トークンの推移。青が単体、橙が協調](/images/astra-sol-isucon/sdk-rerun-20260913/comparison.png)

10万点への到達は単体75.84分、協調83.56分。25万点は協調が約1.1分早く、50万点は単体が158.08分で到達し、協調は未到達でした。途中の一場面だけでも結論は出せません。

## Codex Proで親子をどう制御したか

初回はnative subagentでした。再実行では、両群の親を**公式Codex Python SDK openai-codex 0.154.0によるAstra/high**にし、協調群の子は外部制御器から**Codex CLIのSol/high**として起動しました。ChatGPT ProのCodexログインを使い、APIキーへのフォールバックは設定していません。**Agents SDKからAPIモデルを呼ぶ方式ではありません。**

1. 親が共通メモ・仮説・基準commit・担当パス・検証方法をタスク台帳に登録する。
2. control.pyが専用cloneに子を最大2体起動。指定範囲以外の書込み、Gitメタデータへの書込み、ネットワークをOS sandboxで制限する。
3. 子が差分と根拠を返し、親が検査・commit・独立レビューを進める。
4. 親がexperiment.pyへ候補を渡す。配備・初期化・実行物照合・ベンチ・回収・復元は環境ごとの排他実行器で処理する。

同じ仮説・基準版の修正は同じthreadを再利用し、基準版が変われば新しいattemptで作り直します。親だけの会話履歴を全子へ複製する構成ではありません。

実測は**29子thread、34呼出し（再開5回を含む）、同時最大2体**。全34回でSol/high・隔離検査・正常worker終了・後始末を確認しました。native subagentのspawnは0件です。

## 完了したレビューが28分間、1枠を占有した

読み取りレビューのgroup-commit-reviewは、変更なしで終了しました。しかし台帳の状態がpreparedに残り、同時枠の計算に含まれ続けました。

結果として**1枠を約28分占有し、追加レビューの起動が実際に2回worker capacity reachedで拒否**されました。別の候補が採用され、古い基準版のタスクがstaleになって枠が解放されています。完了した読み取りタスクを直接終端状態にする適切なAPI遷移がありませんでした。

試験中には直さず、固定した制御で最後まで測定しました。次は、読み取り成果物の完了状態、実際に動いているworker数、未評価パッチ数を分けて管理する必要があります。枠の損失は確認できましたが、これで何点失ったかは未測定です。

子が1体以上動いたのは約74.15分、2体が重なったのは約8分です。子の最大入力は53,083tokenに収まった一方、親は244,705token。協調群の記録総トークンの約87.9%は親が使っています。子が動いていない時間には親の調査・レビュー・測定も含まれ、すべてを待機とは呼べません。

総トークンの最終値だけでなく、消費がどの時点で新しい最高値につながったかを見ます。時系列は親子のusage更新を合算し、同じthreadの再開を二重加算していません。締切直前の未報告分は補完していません。

**試行別のドル費用は未計測です。** Proの月額を任意に按分したり、API単価を当てて実請求と呼んだりはしません。EC2は両群とも4台×3時間＝12 instance-hoursを割り当てました。図の資源量の軸は時間の換算で、金額ではありません。準備・再起動確認も時間外です。非キャッシュ入力・出力の内訳、推移の公開CSV、費用として分かる範囲は詳細版に載せています。

## Codex SDKが原因なのか

[公式Codex SDK資料](https://learn.chatgpt.com/docs/codex-sdk)も確認しました。Python SDKはローカルCodex app-serverを操作する仕組みです。今回の仮説選択やタスク台帳は自作しています。

**再実行の単体側もSDK経由なので、両群の点差をSDKの有無では説明できません。** 初回からは隔離、broker、親の実装制約、同時上限なども変わっており、SDKだけの因果効果は未測定です。

原因が特定できたのは、自作coordinatorが完了レビューの枠を解放しなかったことです。親への仕事の集中、子の同時稼働約8分、通常合格runが40対23という差も観測しました。ただし、それぞれで何点失ったかは分かりません。

次はレビューの完了状態と実行枠の数え方を先に修正・検証します。SDK固有の影響を測るなら、同一バイナリ・モデル・指示・ツール・権限を揃え、起動経路だけを変えた応答時間と完了時間の比較が必要です。SDK導入の便利さと、今回のISUCON最適化性能を分けて評価します。

## 初回と何が違うのか

| 時間内最高値 | 初回 | 再実行 |
|---|---:|---:|
| Astra単体 | 1,621,980 | 556,115 |
| Astra＋Sol | 1,114,247 | 409,477 |

初回の再起動後スコアは単体1,636,308、協調885,334でした。初回は協調群が50万点へ約27分早く到達し、最終的には単体が先行しています。その記録は個人サイトに残しました。

再実行では両群とも絶対スコアが下がりました。SDK、broker、隔離、同時上限、台帳、親の実装制約、コンテキストの渡し方をまとめて変更しています。EC2実体や探索経路も異なるため、差をSDKだけの効果にはできません。

再実行の協調群は記録総トークンが単体より約14%、非キャッシュ入力が約69%、出力が約121%多くなりました。キャッシュ入力は入力の内数で、二重加算していません。全31threadの保存済み累積値を集計していますが、両親の最後のturnは締切で中断しています。**未報告分があり得る記録値で、完全な課金メーターではありません。**

## 確認した範囲と後片付け

各群の構成は競技c5.large×3＋ベンチc4.xlarge×1。初回と同じ初期commit・再構築AMIを使いましたが、競技当日のAMIとの完全一致ではありません。準備中の旧バイナリによる4計測は無効化し、初期commitからビルドしたバイナリへ揃えて基準を取り直しました。有効基準は1,627対1,843で、単体はpassですが非致命的減点が1件あります。

試験agentには初回の解答や結果を渡さず、固定対象37ファイルは終了時も一致しました。全台再起動後は両群pass・減点0で、8台のboot ID変更と6台の実行バイナリ一致を確認しています。**その後、8 EC2と対象EBS・ENI・専用SG・鍵をdestroyし、残存0まで検証しました。**

追記はexperiments/codex-sdk-compare/RESULT.mdと最終協調監査に基づきます。各方式1回ずつの結果なので、最適な協調方式を確立したとは言えません。
