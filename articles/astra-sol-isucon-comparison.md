Codexの**Astra単体**と、**AstraがGPT-5.6 Solの子をまとめる構成**を、各3時間・各1試行で比較しました。独立した競技サーバー3台＋ベンチ1台をそれぞれ用意し、計8 EC2で同時に実行しています。

結論は、**今回は単体が最終点とトークン効率で勝ち、複数は中盤の到達速度で先行した**、です。

この記事は実験報告 `experiments/codex-aws-compare/RESULT.md` の要点版です。元の実測グラフを掲載し、実験条件、全トークン内訳、子24体の稼働タイムライン、公開用CSVは個人サイトにまとめました。

## ISUCONを知らない方向けに

ISUCONは、渡されたWebサービスの機能を保ちながら、限られたサーバーで性能を改善する競技です。SQL、キャッシュ、CPU負荷、サーバー配置などに手を入れ、利用者を模したベンチマーカーで正しさと性能を測ります。

**今回測ったのはISUCON11予選の「ISUCONDITION」**です。椅子から届く状態データを保存し、履歴やグラフを表示するサービスで、継続的な書込みと読取り・集計を同時にさばきます。

## 子を呼べたことと、効率よく並列化できたことは別

親は両方 `gpt-6-astra` / high、子は `gpt-5.6-sol` / high、Codex CLIは0.154.0です。

複数側には、調査の分担、仮説単位の実装、専用worktree、実装同時2件までという運用を与えました。配備・初期化・ベンチ・ログ回収は、環境ごとの排他実行器を通しています。

試行専用の子上限は5でしたが、実際の同時稼働は最大3体です。リポジトリの通常設定と試行時の明示設定を分けて確認しています。

native sessionの監査では、子24体すべてが指定した `gpt-5.6-sol` / highで、実装worktreeの分離と実装同時2件以内に反例は見つかりませんでした。

ただし、**子2体以上が同時に動いたのは3時間中約14分半**です。新しい文脈で起動しても、共通マニュアルの読み直しがあり、調査子の入力が大きくなる場面もありました。

両方式とも候補実行は56件。通常合格は単体50件、複数46件、診断は4件と8件、不合格は各2件でした。実験実行器の使用時間は約87分と86分で、ロック待ちはほぼありません。ベンチ待ちが詰まり続けていたわけではありません。

次に改善したいのは子の上限より、親が測定している間に次の独立仮説を準備させる流れです。増員が通常の合格実験数を増やしたかまで追う必要がある、と感じました。

## 親と子をどうつないだか

**controllerが時間とモデルを固定し、親Astraが仕事を割り振り、executorが実機での計測を直列化する**構成です。

1. 親が `spawn_agent` でSolを起動。`fork_turns="none"` とし、目的・基準commit・担当パス・観測・検証方法だけを渡す。
2. 子は専用worktreeで作業し、commit、根拠、検証済み・未検証事項を返す。
3. 親が差分をレビューして現在の基準へ統合。前提が変わった子だけに `send_message` で新commitと変更点を伝える方針にする。
4. 親だけが `experiment.py` に候補を提出。環境別の `flock` が、設定復元・配備・実行物照合・ベンチ・ログ保存を覆う。
5. run IDと実行出力で採否を判断し、次の仮説へ進む。未測定の統合候補は最大1件に抑える。

子による配備や直接SSHは禁止する指示ですが、OS権限で全面的に封じたわけではありません。モデル・起動数・実行区間はnative sessionで監査し、worktreeと実装数はコマンド履歴も照合しました。**設定、指示、実行コード、監査を組み合わせた制御**です。詳しい設定抜粋と受渡し例は個人サイトに載せています。

## この結果で言える範囲

各方式1回の改善試行なので、一般的なモデルの優劣は断定できません。EC2種別・台数はISUCON11の公式構成に合わせましたが、当時のAMIが取得不能だったため復元環境です。物理CPU型番と初期点にも差があります。

また、複数の選定版は同じcommitでも654,392〜1,114,247点と変動し、再起動後には9件の通信エラーと71件のtimeoutが残りました。最終出力は `885334(885350 - 16)` で、直接減点16点だけで最終点の差を説明できません。両方passですが、さらに再起動してデータを読戻す検査とブラウザの追試は未実施です。

約7.50GBのログとソース等を手元に保存しました。実験後は全8 EC2と関連EBS・専用SG・キーペアをdestroyし、9月13日03:14:14 JSTに撤収検証まで完了しています。
